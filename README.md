# septic_torsion

This repository contains the code and the logs of the computations in degree 7 of the paper
*Torsion of elliptic curves over number fields of degree 6, 7, 8 and 9* (F. Najman, 2026). The
statement numbers below are those of the version of November 2026 of that paper. The computations
in the other degrees are in the repositories
[sextic_torsion](https://github.com/F-Najman/sextic_torsion) (degree 6),
[octic_torsion](https://github.com/F-Najman/octic_torsion) (degree 8) and
[nonic-torsion](https://github.com/F-Najman/nonic-torsion) (degree 9); this one is
[septic_torsion](https://github.com/F-Najman/septic_torsion).

In degree 7 the paper proves (Theorem 1.1)

  Φ(7) = Φ^∞(7) ∪ {Z/25, Z/33, Z/36},

so that exactly 41 groups occur as the torsion subgroup of an elliptic curve over a septic field,
and (Theorem 1.2) that an elliptic curve E over a septic field K whose torsion contains Z/25, Z/33
or Z/36 has exactly this torsion group and is, up to isomorphism of the pair (K, E), one of the
pairs of Proposition 13.2 (listed in Table 5): a single one for Z/25 and for Z/33, and two for
Z/36.

The code was first written for a separate version of the proofs in degree 7 alone. In the paper
many statements treat several degrees at once, and in many places a computation in a larger degree
also covers degree 7 (Section 6.1 and Remark 7.4 of the paper), so that some of the computations
here are now only checks. The table in [Which script proves what](#which-script-proves-what) is the
authoritative map from each statement of the paper that rests on a computation in this repository
to the script that verifies it and the log that script produced; for a statement that covers
several degrees it says which case the row covers and where the other cases are proved. The
computations here that the proofs do not need are listed, with the statements they check, in
[Further checks](#further-checks), to which Section 15 of the paper refers. In the digital version
of the paper, the words reporting a computation are links to the script that carries it out. Most
logs can be regenerated with [`verify_all.sh`](#reproducing-the-computations). A few cannot be
regenerated by a single command, because the run was interrupted or continued by hand inside a
Magma session; they are marked "archived" in `jobs.txt`, and the section
[Archive-only logs](#archive-only-logs) explains each of them. The logs are those of the original
runs, byte for byte, apart from the logs of the Python replays, which were regenerated with the
scripts as they stand here; see [Provenance of the committed logs](#provenance-of-the-committed-logs).

This repository is organized like the repositories
[quintic-torsion](https://github.com/F-Najman/quintic-torsion) and
[sextic_torsion](https://github.com/F-Najman/sextic_torsion). Several computations of the sextic
repository are reused here, and their scripts and logs are included; the tables below say which
logs are copies of logs of sextic_torsion.

## Getting the code

The Magma code depends on [mdmagma](https://github.com/koffie/mdmagma), which supplies the
moduli-theoretic routines (`MDX1`, `MDX11`, `HeckeOperator`, `DiamondOperator`, `ModuliPoint`,
`CuspOrbitsQ`) and, through its own `Magma` submodule, Sutherland's optimised models of
`X_1(N)` and `X_1(M,N)`. The point counts use Sutherland's
[GL2 package](https://github.com/AndrewVSutherland/Magma). Both are pinned as submodules, at the
same commits as in sextic_torsion.

```bash
git clone https://github.com/F-Najman/septic_torsion
cd septic_torsion
git submodule update --init                       # mdmagma and gl2
git -C mdmagma submodule update --init Magma      # Sutherland's models, used by mdmagma
git -C mdmagma apply ../mdmagma-magma2.30.patch   # needed with Magma V2.30, see below
```

Do not use `git clone --recurse-submodules`: mdmagma has a further submodule
`tests/magma-unittest` registered under an SSH URL, so a full recursive clone can fail without a
GitHub SSH key. It is not used here.

The pinned commits are mdmagma `d1c019c6` (with its `Magma` submodule at `6a5a68a8`) and the GL2
package at `e70690a`. The latter two are different checkouts of the same repository on purpose:
mdmagma pins a commit that predates `gl2points.m`, so the point-count scripts attach the separate
copy in `gl2/`, and every other script attaches mdmagma's.

**The mdmagma patch.** Magma V2.30 rejects two statements of the pinned mdmagma: an
`end intrinsic` without its semicolon in `v2/curves/divisors.m` and in
`v2/modular_curves/base_curve.m`. All computations here were run with a copy of mdmagma in which
these two semicolons had been added, and nothing else changed. `mdmagma-magma2.30.patch` makes
exactly this change; apply it with the command above. `verify_all.sh` checks whether it is
applied and applies it if not.

## Running the computations

All scripts are run from the repository root; the `Attach`, `AttachSpec` and `load` paths and the
paths `data/...` are resolved from there. Everything was run with Magma V2.30-1. The Python
scripts need Python 3 with SymPy (`python3 -m pip install sympy`); `independent/ranks7.py` also
needs `psycopg2` and network access to the LMFDB mirror. The shell driver requires Bash 4.4 or later
and GNU command-line tools. Magma commands use `-n` to suppress personal startup files.

Several drivers take parameters, passed as `magma -n -b Name:=value script.m`:

* `hecke_sieve.m`, `hecke_sieve_commonzero.m`, `hecke_sieve_smart.m` — the Hecke sieve on
  `X_1(N)`, with parameters `N`, `p`, `Qs`, `D`, `M`, `MemGB`, `Shard`, `NShard`, `FromDegree`,
  `MaxPart`. A run with `FromDegree` or `MaxPart` treats only the partition types of degree at
  least `FromDegree` and largest part at most `MaxPart`, and ends in `SIEVE_RESUME_DONE`. The three
  differ only in caching and in the Hecke routine, and print identical output.
* `cusp_cartier.m` (`TestN:=39`), `N45_cartier_rr.m`, `N51_cartier.m`, `N63_cartier_rr.m` — the
  Cartier criterion at 2, with parameters `D`, `TestN`, `DirectCheck`, `StopAfterExceptions`,
  `Limit`, `MemGB` and `JetFile`, the file to which the certificate is exported.
* `winding_probe.m`, `winding_probe_minimal.m`, `winding_probe_krylov_modp_v2.m` — parameter `N`
  (and `KrylovFile`); `C57_good7_final.m`, `C69_good7_final.m`, `class_mixed_degree7_full.m` —
  parameter `N`.
* `finite_fields_2_degree7.m` — parameters `Ns`, `Ps`, `K`.
* `N42_test7_shard.m` (`Shard`, `NShard`), `N42_mixed34_shard.m`, `sieve_42_fixed_shard.m`,
  `n28_degree7_hecke_shard.m` (`Shard`), `verify_n24_reducible_witnesses.m` (`Index`).
* `rational_two_torsion.m`, `two_torsion_49_T2.m` — `MatrixFile` (and `N`, `Qs`), to export the
  integral matrices that the Python replays read.

Everything else runs without parameters. The commands that produced the committed logs are in
`jobs.txt`. For example:

```bash
magma -n -b N:=34 M:=1 p:=3 D:=7 Qs:=5,7,11 hecke_sieve.m
magma -n -b D:=7 N51_cartier.m
magma -n -b Shard:=3 NShard:=8 N42_test7_shard.m
python3 replay_fi_jets.py data/N51_cartier_kernels.m
```

Magma may buffer its output, so a terminated run can leave an empty or incomplete log, and some
Magma errors return exit status 0. Check both the exit status and the closing marker: every
script prints a marker when it finishes, and the third column of `jobs.txt` gives it for each
log. Many scripts end without `quit;`; run them with standard input at end of file
(`< /dev/null`), as `verify_all.sh` does, so that Magma exits when the script ends.
`hecke_cusp_correction.m` writes its log itself, so its command in `jobs.txt` discards the
standard output.

## Reproducing the computations

`jobs.txt` lists each log file, the command that produces it, and its closing marker. An optional
fourth column gives an expected result as an extended regular expression.

```bash
./verify_all.sh                 # every job, Magma jobs one at a time
./verify_all.sh -j 4            # Magma jobs four at a time
./verify_all.sh c42             # only the jobs whose log path contains c42
./verify_all.sh -j 4 cartier    # both
python3 -m unittest discover -s tests   # the driver's tests; no Magma needed
git diff                        # what the rerun changed
```

The driver overwrites the selected logs in place; `git diff` compares the new output with the
committed run. It runs the selected Magma jobs first, then the Python jobs one at a time and in
the order of `jobs.txt`, because the Python jobs read the logs and data files written by the
Magma jobs. When Magma jobs are selected, the driver first applies the mdmagma patch if necessary
and then attaches every package once, in separate processes, so that parallel jobs do not compile
the same signature files at the same time.

A job passes only if its command exits 0, its closing line is the expected marker (optionally
followed by a space and details), and any result expression matches. The closing line is the
last non-blank line of the log, ignoring carriage returns, a trailing `Script done on ...` line
written by `script(1)`, and trailing lines that consist of a CPU time only. The markers omit the
CPU times at the end of the closing lines. As Magma reports most errors on standard output,
carries on and exits with status 0, a job also fails if its log reports a Magma error.

Rerunning all jobs costs about 17 hours of CPU time, most of it on the eight shards of the type
[7] on `X_1(42)` (about 47 minutes each), the Cartier test on `X_1(45)`, the class computation on
`X_1(2,24)` and the four shards of the type [3,4] on `X_1(42)`.

The jobs that export data rewrite the corresponding files in `data/`. Some computations choose
representatives in an order that Magma does not fix: a representative of a diamond orbit, a curve
in an isomorphism class, the order in which places are listed, random test curves. A rerun can
therefore print different representatives (for instance on the `SURVIVOR` lines of
`logs/sieve/X1_32_p3.log`) and write the same records in a different order, as
`N42_export7.m`, `N42_export_mixed34.m` and `N54_good7_bsgs.m` do. The sharded tests and the
audits refer to the committed order of these records, and `audit_42_degree7.py` checks the
SHA-256 of the committed tables. So rerun an export only together with the jobs that read it, or
restore the committed file with `git checkout` before rerunning those jobs.

What a successful reproduction should change, and nothing else:

* timing figures, including the `time=...` fields and the bare CPU times;
* the choice of representatives and the order of records described above;
* the transcript lines of `logs/tests/probe_42_hecke_hash.log`, which was recorded on a terminal,
  and the paths in Magma's `Loading "..."` lines, which name the original working directories;
* whitespace, and whatever a different version of Magma prints differently, such as the printed
  form of a model or an ideal, or the order of the elements in a printed set.

Everything else is a genuine discrepancy: the place counts, the Hecke primes and cusp conditions,
every `RESULT`, `SURVIVOR` and `SUMMARY` line, the group invariants and class-membership results,
the dimensions and ranks of the Riemann–Roch and Cartier tests, and the closing markers.

### Archive-only logs

These logs are kept because a proof or one of the [further checks](#further-checks) uses them,
but no single command regenerates them. Each is listed in `jobs.txt` with the command
`archived: ...`, and is not rerun by `verify_all.sh`.

* `logs/x1_36/quotient_filter.log` — the class computation for the septic points on `X_1(36)`
  (Proposition 13.10). It was carried out in one interactive Magma session, which ran
  `probe_36_class5_v2.m` (the groups `J(F_5)` and `H`), `prepare_36_degree7_orbits.m` (the
  diamond representatives), `quotient_36_to_2_18.m` (the map to `X_1(2,18)`), then
  `class_36_quotient_filter.m`, which wrote this log, then `class_36_known_lifts_orbits.m` and
  `export_36_quotient_certificate.m`, which wrote `data/certificate_36_quotient_data.py`, and
  `check_36_coordinate_presentations_v2.m`, which checks the presentations of the two groups used
  and wrote `logs/x1_36/coordinate_presentations.log` (also archived) and
  `data/coordinate_presentations_36_data.py`. The session was interrupted once and reported two
  errors along the way, and its other output was not kept, so there is no log of the first three
  steps. `certify_septimic_36.m` chains all the steps except `check_36_coordinate_presentations_v2.m`
  in one run, but it was never run as a whole. The numbers that were kept are consistent with each
  other and with the paper. `replay_36_quotient_certificate.py` replays the class arithmetic of
  the exported certificate independently with integer arithmetic
  (`logs/x1_36/quotient_replay.log`), and `verify_known_36.m` checks the known points in a fresh
  run.
* `logs/c42/lower7.log` — `N42_lower7.m`, which completed the 33 tests of the type [4] on
  `X_1(42)` and was stopped during its tests of the type [3,4]. Only the 33 quartic tests are
  used (Proposition 6.5); the type [3,4] was redone in the four shards of `N42_mixed34_shard.m`.
* `logs/c42/degree6_prefix_session.log` — the terminal transcript of the `X_1(42)` sieve of the
  sextic computation (`hecke_sieve_42_roots.m`), which completed the types [3], [4], [5] and was
  interrupted during [6]; `export_42_fixed_reps.m` was then loaded into the same session, wrote
  the 392 sextic representatives to `data/c42_fixed_representatives.m` and tested the 8 divisors
  of type [3,3]. It is the same log as `logs/sieve/X1_42_p5_prefix_session.log` of sextic_torsion.
  The types [3], [5], [6] and [3,3] are used in Proposition 6.5 (the type [6] through the four
  shards of `sieve_42_fixed_shard.m`, whose logs are also those of sextic_torsion), with Hecke
  primes that are admissible in degree 7; the quartic tests of this run are not used, since the
  cuspidal complement is larger in degree 7. `audit_42_degree7.py` checks all of this.
* `logs/sieve/X1_49_p3_prefix.log` — the interrupted `X_1(49)` sieve of the sextic computation
  (`hecke_sieve_cached.m`; it is `logs/sieve/X1_49_p3_prefix.log` of sextic_torsion), whose
  completed types of degree 4 and 5 are the computation that Proposition 6.10 cites, in
  sextic_torsion, for the points of degree 4 and 5.
* `logs/sieve/X1_40_p3_first_attempt.log` — a first sieve on `X_1(40)` with `hecke_sieve.m`,
  stopped during the type [7]. It is superseded by `X1_40_p3_lower.log` and `X1_40_p3_septic.log`;
  it is kept because `audit_cusp_correction.py` checks that its survivor of degree 5 is the one
  of the fresh run, and `data/N40_survivors.txt` was extracted from it.
* `logs/m2/X1_2_28_sieve_interrupted.log` — `sieve_2_28_degree7.m`, which completed the types
  [5] and [6] on `X_1(2,28)` and was interrupted during [7]. `audit_n28_degree7_hecke.py` extracts
  the completed part into `data/N28_D7_lower_completed_prefix.log`; the type [7] was redone with
  `export_n28_degree7_hecke.m` and the two shards of `n28_degree7_hecke_shard.m`. This computation
  is now a check of Proposition 11.3 (see [Further checks](#further-checks)).
* `logs/counts/independent_counts.log` — `independent_counts.m`, stopped by hand during its last
  curve. `independent_counts_fast.m` repeats all seven counts; the six completed lines are read by
  `audit_sieves.py`.

## Provenance of the committed logs

The computations were run in the working directories of the original record, with paths relative
to its root (`work/degree7/...`) or absolute. For this repository the files were moved into the
present layout and every path in the scripts was rewritten accordingly; apart from paths, the
Magma scripts are identical to the versions that ran, with one exception: Magma's `Write` appends
to an existing file, so that a rerun replaces the exported data instead of appending to the
committed copy, the first write to each exported file now has the option `Overwrite:=true` (and
`N63_cartier_rr.m` truncates its default export file). The committed data files each hold the
output of one run, except `data/A3_D7_RR_records_v2.txt`, which holds two identical copies written
by two runs of `filter_2_30_degree7_a3_first.m`; `replay_m230_degree7_reverse.py` accepts one or
two copies. The committed Magma logs are those of the original runs.

Several helper files existed in more than one copy in the original record; identical copies were
merged. Two of them existed in two versions, both of which are used: `fast_hecke_11_v1.m` and
`fast_hecke_cyclic_commonzero_v1.m` are the earlier versions of `fast_hecke_11.m` and
`fast_hecke_cyclic_commonzero.m`.

The Python audits and replays were adapted to the present layout: they read and write the paths
here, and the checks of the SHA-256 hashes of the original working files (which bound the files of
the original record together) were removed, since the git history now does this. Their logs were
regenerated with the scripts as they stand here, and agree with the original logs, except that
`logs/m2/X1_2_24_coverage.log` and `logs/m2/X1_2_28_coverage.log` record the SHA-256 of a Magma
script whose paths were rewritten. Some Python jobs had no log in the original
record; their logs were produced for this repository.

Further points a reproduction should be aware of:

* Several computations were run twice in the original record, the second time while auditing.
  Where both logs exist, the one kept here is the complete run (for `X_1(69)` the fresh run
  `logs/n57_n69/C69_cover.log`, rather than a continuation); the others are not included.
* The drivers of the sieves on `X_1(32)`, `X_1(34)`, `X_1(38)` (`hecke_sieve.m`) and on `X_1(35)`,
  `X_1(39)` (`hecke_sieve_commonzero.m`) are inferred from the file times; see `jobs.txt`.

## Hardware

The computations were run on the server Mordell at the University of Zagreb, with an AMD EPYC
9175F CPU (16 cores, 32 threads) and 384 GB of RAM, using Magma V2.30-1. The committed runs took
about 19 hours of CPU time in total (the CPU times recorded in the logs, counting interrupted runs
up to the interruption, and including the computations of the sextic repository whose logs are
included here). The longest single computations were the Cartier test on `X_1(45)` (4108 s), the
class computation on `X_1(2,24)` (3631 s), the `X_1(36)` class filter (3059 s) and the eight shards
of the type [7] on `X_1(42)` (about 2800 s each).
